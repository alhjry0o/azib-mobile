# DECISIONS — سجل القرارات المعماريّة (ADR)

> كل قرار تقني/معماري مؤثر يُسجَّل هنا. صيغة ADR متبعة أدناه.
> لا يُغيَّر قرار **Accepted** إلا بـ ADR جديد يشير إلى القديم ويشرح سبب التغيير، وبموافقة مالك المشروع.
> **عام المستودع:** لا أسرار ولا بيانات حقيقية.

---

## قالب ADR

### ADR-XXXX — عنوان القرار
- التاريخ: YYYY-MM-DD
- الحالة: Proposed | Accepted | Superseded by ADR-XXXX | Deprecated
- السياق: لماذا نحتاج هذا القرار؟ ما القيود؟
- القرار: ماذا اخترنا بالضبط؟
- البدائل المدروسة: ماذا رُفض ولماذا؟
- التبعات: الإيجابيات، السلبيات، ما الذي يصبح أصعب؟
- معايير المراجعة: متى نعيد النظر؟
- المراجع: ملفات/روابط.

## ADR-0001 — استخدام npm بدل pnpm
- **التاريخ:** 2026-11-08
- **الحالة:** Accepted
- **السياق:** المشروع يستخدم Expo، وExpo لديه مسار مدعوم وأكثر اختباراً مع npm. pnpm يضيف طبقة تعقيد (node linker, hoisting) قد تتعارض مع بعض إضافات Expo.
- **القرار:** اعتماد **npm** كمدير الحزم الوحيد في المستودع وCI. لا `pnpm-lock.yaml`، لا `yarn.lock`، لا `bun.lockb`.
- **البدائل المدروسة:** pnpm (أسرع، موفّر للمساحة، لكن دعم Expo أقل اختباراً)؛ yarn (لم يُطلب).
- **التبعات:** + متوافق مع `npx expo install` افتراضياً. − استهلاك مساحة أكبر لـ `node_modules`.
- **معايير المراجعة:** إذا صار Expo يدعم pnpm رسمياً ومُختبراً، يُفتح ADR بديل.
- **المراجع:** `docs/AGENT_RULES.md`، وثائق Expo (تُراجع في P02).

## ADR-0002 — Zustand (حالة العميل) + TanStack Query (حالة الخادم)
- **التاريخ:** 2026-11-08
- **الحالة:** Accepted
- **السياق:** نحتاج فصلاً واضحاً بين حالة واجهة قصيرة العمر (theme, locale, onboarding flags) وحالة خادم (بيانات المستخدم، الطلبات، الشركاء).
- **القرار:** Zustand للحالة المحلية/الواجهة فقط، TanStack Query لكل قراءة/كتابة على الخادم. لا تخزين بيانات خادم في Zustand.
- **البدائل المدروسة:** Redux Toolkit (أثقل من اللازم)؛ Context API كبديل عام (لا يصلح لحالة خادم معقدة).
- **التبعات:** + فصل مسؤوليات واضح. − منحنى تعلّم لـ Query keys وسياسات `staleTime`.
- **معايير المراجعة:** إذا تسبّب التنازع في أخطاء متكررة ناتجة عن تكرار المصدر.
- **المراجع:** HRD (المكدس).
- **تحديث P05 (2026-11-16):** فُعّل Query فعلياً؛ الجلسة في Query لا Zustand، ومفتاحها يحوي AppMode.
- **تحديث P06 (2026-11-16):** ستة متاجر عميل (app-mode · onboarding · shell · language · auth · settings) — كلها بلا توكنات أو بيانات خادم. حالة الضيف علم محلي؛ الملف الشخصي والجلسات والموافقات في Query. رابط الصورة في Query cache (ADR-0020).

## ADR-0003 — 3D بثلاث طبقات
- **التاريخ:** 2026-11-08
- **الحالة:** Accepted
- **السياق:** الهوية البصرية تريد عمقاً وحساً Premium Dark، لكن 3D ثقيل قد يضر بالأداء وأجهزة السوق (Android متوسط/ضعيف).

- **معايير المراجعة:** إذا صار الأداء ممتازاً على الأجهزة المستهدفة وطُلبت طبقة إضافية.

## ADR-0005 — نموذج Non-Custodial
- **التاريخ:** 2026-11-08
- **الحالة:** Accepted
- **السياق:** المنصة غير ربحية وليس لديها ترخيص/بنية لحفظ أموال المستخدمين. أي حفظ أموال يجرّ التزامات قانونية وأمنية ثقيلة.
- **القرار:** لا محفظة داخل التطبيق، لا Escrow، لا تحويل داخلي. ما تعرضه المنصة **سجل مساعدة** لا حساب أموال. التبرعات الحقيقية تُسجَّل فقط عبر مزوّد مرخّص متحقق منه خارج التطبيق. لا نظام دفع تجريبي يُنتج إيصالاً حقيقياً.
- **البدائل المدروسة:** محفظة داخلية (مرفوضة لتعقيدها القانوني والأمني).
- **التبعات:** + مسؤولية قانونية وأمنية أقل. − التطبيق لا «يحوّل» أموالاً؛ كل تفاعل مالي خارجي.
- **معايير المراجعة:** لا — قرار استراتيجي. أي تغيير يحتاج ADR بديلاً وموافقة المالك.
- **المراجع:** HRD، `AGENT_RULES §1 #21`، `THREAT_MODEL.md`.

## ADR-0008 — eslint-import-resolver-typescript لحل مسارات `@/`
- **التاريخ:** 2026-11-09
- **الحالة:** Accepted
- **السياق:** `eslint-plugin-import` لا يفهم path aliases من `tsconfig.json` افتراضياً ⇒ أخطاء كاذبة على `@/…`.
- **القرار:** إضافة `eslint-import-resolver-typescript` وإعداد:
```js
settings: {
  'import/resolver': {
    typescript: { project: './tsconfig.json' },
  },
}
```
  مصدر الحقيقة للمسارات يبقى `tsconfig.json`.
- **البدائل المدروسة:** resolver-alias مع تكرار المسارات (يخالف مصدر حقيقة واحد)؛ تعطيل `import/no-unresolved` (يفقد فحصاً مهماً).
- **التبعات:** + لا تكرار، وانعكاس تلقائي لأي تعديل. − ارتباط بـ`tsconfig.json`.
- **معايير المراجعة:** تغيّر واجهة settings أو دعم أصلي في ESLint 10.
- **المراجع:** `eslint.config.js`، `tsconfig.json`، `AGENT_RULES §1 #8`.

## ADR-0011 — Jest mock لـreact-native-reanimated
- **التاريخ:** 2026-11-14
- **الحالة:** Accepted
- **السياق:** `jest-expo` لا يفعّل `react-native-worklets/plugin`، فأي استيراد من Reanimated يفشل بخطأ worklet. لا mock رسمي مضمّن لـReanimated 4.
- **القرار:** mock يدوي كامل في `jest.setup.ts`: Animated.* → مكونات RN · `useSharedValue` → كائن عادي · `useAnimatedStyle` → تنفيذ مرة واحدة · `with*` → القيمة النهائية · Gesture chainable no-op.
- **البدائل المدروسة:** `setUpTests()` (يفشل مع v4)؛ `reanimated/mock` (مسار قديم)؛ عدم استخدام Reanimated (يخالف الـbrief).
- **التبعات:** + ثبات كل اختبارات الحركة. − الحركة الفعلية لا تُختبر في Jest؛ ترقيات v5 قد تكسر الـmock.
- **معايير المراجعة:** توفير mock رسمي أو استقرار `setUpTests()`.
- **المراجع:** `jest.setup.ts`, `DoubleRingLoader.tsx`, `Hero3D.tsx`.
- **تحديث P05/P06:** استُخدم نفس الـMock دون تعديل. أُضيفت mocks عالمية لـNetInfo وexpo-splash-screen وexpo-secure-store وexpo-image-picker وexpo-image-manipulator. mocks الحزم الجديدة في P06.3 (file-system/sharing/local-authentication) **محلية في ملفات الاختبار** لأن `jest.setup.ts` كان معدَّلاً خارج الجلسة.

## ADR-0012 — FloatingDock مخصص فوق Expo Router Tabs
- **التاريخ:** 2026-11-16
- **الحالة:** Accepted
- **السياق:** الهوية تطلب شريطاً عائماً زجاجياً بخانة وسطى مميزة وحركة اختيار وشارة وإخفاء عند الكيبورد واحترام Safe Area وترتيب RTL. شريط `Tabs` الأصلي لا يوفّر ذلك، وتخصيصه يقيّدنا بواجهة تبعية غير مباشرة.
- **القرار:** `<Tabs>` مع إخفاء الشريط الأصلي (`tabBar` **prop مباشر** لا داخل `screenOptions`) + رسم `FloatingDock` كطبقة overlay فوق `GlassView`. التنقل بـ`useRouter().navigate()`، والنشاط بـ`usePathname()` + `isTabActive()` نقية. الترتيب من `TABS` مع `flexDirection: isRTL ? 'row-reverse' : 'row'`. الشارة من `useNotificationsBadge()` (0 = مخفية بصدق). الإخفاء بـ`useKeyboardVisible()`.
- **البدائل المدروسة:** `tabBar` بواجهة `@react-navigation/bottom-tabs` (تبعية غير مباشرة)؛ `tabBarStyle` فقط (لا يحقق المطلوب)؛ مكتبة خارجية (تخالف قاعدة التحقق).
- **التبعات:** + تحكم كامل واختبارات RTL/كيبورد/شارة، بلا تبعية جديدة. − `paddingBottom` يدوي في الشاشات؛ منطق النشاط مسؤوليتنا.
- **معايير المراجعة:** API رسمي لشريط عائم، أو الحاجة لأكثر من 5 تبويبات.
- **المراجع:** `FloatingDock.tsx`, `TabsShell.tsx`, `constants/routes.ts`.

## ADR-0013 — حفظ اللغة في Zustand وتطبيق الاتجاه عند التبديل والإقلاع
- **التاريخ:** 2026-11-16
- **الحالة:** Accepted
- **السياق:** `setLanguage()` كان يغيّر i18next فقط، و`forceRTL` غير مستدعى، وأثره لا يكتمل إلا بعد إعادة الفتح. مع اختيار اللغة في Onboarding والإعدادات كان المستخدم سيعود إلى `ar` قسراً — وعد غير صادق.
- **القرار:** `language.store` (persist) + `useLanguageSwitch()` نقطة دخول وحيدة (حفظ → `applyDirectionToNativeLayer` → `setLanguage`) + `LanguageBootstrap` يطبّق المحفوظ عند الإقلاع. **لا مكتبة restart**؛ ملاحظة صادقة معروضة بأن الاتجاه الأصلي يكتمل بعد إعادة الفتح.
- **البدائل المدروسة:** مكتبة restart (تبعية غير متحقق منها وتجربة قطع)؛ الحفظ داخل i18n init (تهيئة غير متزامنة)؛ عدم الحفظ (يخالف الصدق).
- **التبعات:** + لغة ثابتة و`forceRTL` فعّال. − الاتجاه لا يكتمل لحظياً.
- **معايير المراجعة:** توفّر مسار إعادة تشغيل موثوق رسمياً.
- **المراجع:** `language.store.ts`, `use-language-switch.ts`, `LanguageBootstrap.tsx`, `i18n/rtl.ts`.

## ADR-0014 — قائمة سماح للروابط العميقة (`azib://`)
- **التاريخ:** 2026-11-16
- **الحالة:** Accepted
- **السياق:** أي رابط مجهول أو موجّه لمنطقة محمية قد يكشف سطحاً غير مقصود أو يمرر معاملات حساسة.
- **القرار:** `deep-links.ts` دوال نقية بثلاثة تصنيفات: **allow** (وجهات عامة) · **guarded** (`/onboarding*`, `/staff*`, `/dev*`, `/gallery*` يقرّر حارس الـLayout) · **not-found** (كل ما عداها)، و**ignore** لغير `azib://`. التطبيع يزيل المجموعات و**يسقط `?query` و`#fragment` بالكامل**. `DeepLinkGuard` يستبدل المجهول بـ`/+not-found`.
- **البدائل المدروسة:** الاعتماد على مطابقة Router فقط؛ denylist (تنسى الجديد)؛ قراءة معاملات الرابط (باب تسريب).
- **التبعات:** + سلوك أمني متوقع ومُختبَر. − كل مسار جديد يحتاج إضافة صريحة (احتكاك مقصود).
- **معايير المراجعة:** دعم Universal Links أو مسارات محمية جديدة.
- **المراجع:** `deep-links.ts`, `DeepLinkGuard.tsx`, `AGENT_RULES §1 #19`.
- **تحديث P06:** أُضيفت مسارات auth الستة، وprofile، وsettings الاثنا عشر، وlegal الخمسة. الحراس داخل الشاشات تظل فعّالة حتى للمسارات المسموحة.

## ADR-0015 — فاحص الأزرار الميتة كبوابة CI
- **التاريخ:** 2026-11-16
- **الحالة:** Accepted
- **السياق:** قاعدة «لا تطبيق وهمي» كانت تُفحص يدوياً. مع نمو المسارات نحتاج فحصاً آلياً يمنع المعالجات الفارغة وعلامات العمل غير المنجز.
- **القرار:** `scripts/check-dead-buttons.mjs` يفشل على معالج `on*` فارغ (`() => {}`, `() => null`, `() => undefined`, `function(){}`, `noop`, مع async ومعاملات) أو `TODO`/`FIXME`. **النطاق `app/` و`src/features/` فقط**، باستثناء `app/(dev)/gallery.tsx` ومجلدات `__tests__`. خطوة CI مستقلة قبل Typecheck. البديل الصحيح: `disabled` بسبب، أو تنقل حقيقي، أو Not Connected صادق.
- **البدائل المدروسة:** قاعدة ESLint مخصصة (تحتاج plugin وصيانة AST)؛ توسيع النطاق لـ`components/**` (يرفض Showcase مشروعاً)؛ فحص يدوي.
- **التبعات:** + منع آلي لانحدار الأزرار الميتة. − regex لا يغطي كل الأنماط؛ غير مضمّن في سكربت `lint` حالياً.
- **معايير المراجعة:** توفر `package.json` محدث (يُضم لـ`lint`) أو الحاجة لتحليل AST.
- **المراجع:** `check-dead-buttons.mjs`, `tests/__tests__/scripts/check-dead-buttons.test.ts`, `ci.yml`.

## ADR-0016 — توسيع عقد `AuthProvider` إضافةً فقط (15 capability)
- **التاريخ:** 2026-11-16
- **الحالة:** Accepted
- **السياق:** عقد P03 كان 4 دوال فقط. P06 يحتاج تسجيل/تحقق/استعادة/تغيير كلمة مرور/جلسات/حذف/تصدير. القاعدة `§1 #12,#13` تمنع كسر عمل ناجح، و`§1 #14` تمنع استدعاء واجهات غير موجودة، وHRD يطلب «جاهز لـSupabase دون تغيير الواجهات».
- **القرار:**
  - إضافة **11 دالة** على مرحلتين (5 في P06.1 + 6 في P06.3) دون حذف أو تغيير أي توقيع قائم ⇒ **15 capability**.
  - تنفيذ كل دالة في **Mock وNotConnected معاً** في نفس الجزء (وإلا فشل اختبار «capabilities موجودة كدوال»).
  - `AuthUser.roles` و`consents` **اختياريان**، و`AuthSession.tokens`/`pendingVerification` اختياريان ⇒ كل كائنات P03/P05 تبقى صالحة.
  - `channels` حقل صريح: المزوّد التجريبي `['email']` فقط — **لا افتراض لـSMS**.
  - **إعادة المصادقة داخل العمليات الحساسة**: `changePassword` يطلب الكلمة الحالية، و`requestAccountDeletion` يطلب كلمة المرور. لا دالة `reauthenticate` منفصلة (تكرار لا حاجة له).
  - الأدوار تُقرأ من الجلسة؛ `hasStaffRole` يرفض عند غيابها. نية التسجيل ليست دور فريق.
- **البدائل المدروسة:** خدمة منفصلة تلتف على العقد (مسار موازٍ يخالف HRD)؛ حقول إلزامية (تكسر كل الاختبارات)؛ افتراض قناة هاتف (يخالف الصدق).
- **التبعات:** + واجهة واحدة جاهزة لـP18، وصفر انحدار. − ملف Mock تجاوز 300 سطر (تبرير `§1 #11`: حالة داخلية مشتركة؛ التفكيك في P18).
- **معايير المراجعة:** عند بناء adapter Supabase في P18، أو الحاجة لقناة هاتف حقيقية.
- **المراجع:** `providers/contracts/auth.ts`, `providers/mock/auth.ts`, `providers/not-connected/index.ts`, `docs/INTEGRATIONS.md`.

## ADR-0017 — TokenVault: SecureStore على الجهاز، ذاكرة فقط على الويب
- **التاريخ:** 2026-11-16
- **الحالة:** Accepted
- **السياق:** HRD يطلب تخزين التوكنات في SecureStore. الحزمة غير مدعومة على الويب، والكتابة في AsyncStorage هناك تُضعف الأمان بلا داعٍ.
- **القرار:** وحدة `token-vault.ts` بواجهة `{persistent, save, read, clear}`: على الجهاز SecureStore بخيار `WHEN_UNLOCKED`؛ على الويب **ذاكرة فقط** (`persistent=false`). عند فشل Keychain نحتفظ بنسخة الذاكرة ولا نرمي. **لا تسجيل للتوكن**، ولا وضعه في Zustand أو Query keys أو الروابط. المسح عند الخروج مع `queryClient.clear()`.
- **البدائل المدروسة:** AsyncStorage على الويب (أضعف أمنياً)؛ رفض العمل على الويب (يخالف مسار التحقق الأساسي)؛ تشفير يدوي في localStorage (تعقيد بلا ضمان).
- **التبعات:** + سلوك أمني واضح وقابل للاختبار. − جلسة الويب لا تصمد أمام إعادة التحميل؛ استعادة الجلسة عند الإقلاع مؤجلة لـP18 (§8 #35).
- **معايير المراجعة:** دعم رسمي لتخزين آمن على الويب، أو تنفيذ استعادة الجلسة في P18.
- **المراجع:** `features/auth/token-vault.ts`, `use-auth.ts`, `docs/INTEGRATIONS.md §3`.

## ADR-0018 — OTP تجريبي حتمي داخل الجلسة (بلا إعادة طلب)
- **التاريخ:** 2026-11-16
- **الحالة:** Accepted
- **السياق:** المزوّد التجريبي لا يرسل SMS/بريداً حقيقياً، ويجب أن يعمل التدفق دون شبكة (`§1 #18`). أول تنفيذ استدعى `requestVerification` بعد `signUp` فوراً، فاصطدم بالكولداون (30s) وفشل التحقق.
- **القرار:**
  - الرمز **حتمي** مشتق من معرّف التحدي، ويظهر بوسم Demo في شاشة التحقق وأدوات Dev.
  - `PendingVerification` يحمل `challengeId?` و`demoCode?` (حقلا demo فقط، لا يظهران في رد خادم حقيقي).
  - **`signUp` لا يستدعي `requestVerification`**؛ يستخدم ما في الجلسة. الاستدعاء مقصور على زر إعادة الإرسال.
  - الكولداون المحلي يبدأ عند **محاولة** الإرسال (نجاحاً أو فشلاً) ليرى المستخدم تقدماً فورياً.
  - الحدود: 5 محاولات للرمز، 30 ثانية لإعادة الإرسال، قفل الدخول بعد 5 إخفاقات.
- **البدائل المدروسة:** قبول أي 6 أرقام (يخفي الأخطاء ويعطي نجاحاً وهمياً)؛ إرسال بريد حقيقي في demo (يخالف `§1 #18`)؛ رمز عشوائي غير معروض (يجعل التدفق غير قابل للإكمال).
- **التبعات:** + تدفق كامل قابل للاختبار بلا شبكة. − حقلان demo-only في العقد يجب ألا يصدرا من خادم حقيقي (موثَّق ومُختبَر).
- **معايير المراجعة:** ربط مزوّد بريد/SMS حقيقي في P18 ⇒ إخفاء الحقلين من رد الخادم.
- **المراجع:** `providers/mock/auth.ts`, `features/auth/use-otp.ts`, `use-auth.ts`, `screens/VerifyScreen.tsx`.

## ADR-0019 — تسلسل الموقع داخل `Profile.city` + شجرة locations تجريبية
- **التاريخ:** 2026-11-16
- **الحالة:** Accepted
- **السياق:** HRD يطلب محافظة ← مديرية ← منطقة من جدول locations. عقد `Profile` يحوي `city: string|null` فقط، وتعديل العقد ممنوع في هذه المرحلة (Contract Tests).
- **القرار:**
  - `Profile.city` يخزّن **معرّف أعمق موقع مختار** (منطقة/مديرية/محافظة).
  - السلسلة الكاملة تُشتق من شجرة `mocks/seed/locations.ts` عبر دوال نقية (`locationChain`, `selectionFromId`, `deepestId`, `isValidChain`).
  - الشجرة تحمل `nameKey` (مفاتيح i18n لا نصاً حرفياً) + `dataOrigin='demo'` + `verificationStatus='pending-human-review'`.
  - التحقق من سلامة الأب/الابن قبل الحفظ؛ تغيير الأب يصفّر الأبناء.
- **البدائل المدروسة:** توسيع عقد Profile بثلاثة حقول (يكسر Contract Tests ويحتاج ADR أكبر)؛ تخزين سلسلة نصية مفصولة (هشّ وغير قابل للاستعلام)؛ جدول locations حقيقي الآن (سابق لأوانه قبل P18).
- **التبعات:** + تسلسل كامل بصفر تعديل عقد، وفلترة `city` تعمل كما هي. − الحقل يحمل معرّفاً لا اسم مدينة (دلالة موسَّعة موثَّقة)؛ البيانات بانتظار تحقق بشري.
- **معايير المراجعة:** P18 ⇒ جدول locations حقيقي + ترحيل `city` إلى `locationId` مع ADR بديل.
- **المراجع:** `mocks/seed/locations.ts`, `features/profile/locations.ts`, `components/LocationCascade.tsx`.

## ADR-0020 — صورة Avatar: قص مركزي + إعادة ترميز + رابط في Query cache
- **التاريخ:** 2026-11-16
- **الحالة:** Accepted
- **السياق:** HRD يطلب صورة اختيارية بقص وإزالة EXIF قبل الرفع. لا مكتبة قص تفاعلية متوافقة مع Expo managed، وعقد `Profile` بلا حقل صورة.
- **القرار:**
  - **قص مربع مركزي تلقائي** + تحجيم 512 + إعادة ترميز JPEG عبر `expo-image-manipulator` (الواجهة المثبتة `manipulateAsync`)، مع معاينة قبل الرفع.
  - **فشل المعالجة ⇒ لا رفع إطلاقاً** (حماية خصوصية افتراضية: لا نرفع ملفاً غير مُعالَج قد يحمل EXIF).
  - الرفع عبر **نفس `FileStorageProvider`** المستخدم في الإنتاج.
  - الرابط يُحفظ في **Query cache** (طبقة حالة الخادم، ADR-0002) بمفتاح per-user، مع ملاحظة صادقة بأن الحفظ الدائم يأتي في P18.
  - `Avatar` يقبل `uri` كخاصية **إضافية** مع رجوع للأحرف الأولى.
- **البدائل المدروسة:** مكتبة قص تفاعلية (تبعية غير متحقق منها)؛ تخزين الرابط في Zustand (يخالف ADR-0002)؛ رفع الملف الأصلي عند فشل المعالجة (يخالف الخصوصية).
- **التبعات:** + مسار خصوصية آمن وصفر تعديل عقد. − الصورة لا تصمد أمام إعادة التشغيل (§8 #26)؛ إزالة EXIF غير متحققة على جهاز (§8 #27).
- **معايير المراجعة:** P18 (عمود دائم + Storage حقيقي) وP20 (تحقق EXIF على أجهزة).
- **المراجع:** `features/profile/image-pipeline.ts`, `use-avatar-upload.ts`, `components/ui/Avatar.tsx`.

## ADR-0021 — حذف بفترة تأكيد + تصدير JSON + سجل وثائق قانونية بنسخ
- **التاريخ:** 2026-11-16
- **الحالة:** Accepted
- **السياق:** HRD يطلب حذف حساب متعدد الخطوات يشرح ما يُحذف/يُجهَّل/يُحتفظ به قانونياً مع فترة تأكيد، وتصدير JSON بالمشاركة، وخمس وثائق قانونية بنسخ. مدة الاحتفاظ قرار بشري غير معتمد (`PRODUCT_POLICIES #7`).
- **القرار:**
  - **الحذف**: 3 خطوات (شرح ← تأكيد ← مجدول). التأكيد يطلب كلمة المرور + كلمة `DELETE` + إقراراً. المزوّد يسجّل طلباً حقيقياً بـ`scheduledFor` و`gracePeriodDays` و`policyStatus: 'pending-human-approval'`، ويوفّر إلغاءً فعلياً. **التنفيذ النهائي مهمة خادم في P18** — معروض بصدق، والمدة موسومة `PENDING_POLICY`.
  - **التصدير**: مستند `schemaVersion: 1` يجمع بيانات الحساب + الملف + التفضيلات، **بلا توكنات أو كلمات مرور أو بيانات مستخدمين آخرين** (مُختبَر). الجهاز: `File`/`Paths` ثم `Sharing` (أو حفظ فقط إن المشاركة غير متاحة). الويب: Blob + تنزيل.
  - **Legal**: سجل `LEGAL_DOCUMENTS` بخمس وثائق، لكل منها `version` و`requiresLegalReview: true` ومفاتيح i18n فقط. النصوص قوالب موسومة «يتطلب مراجعة قانونية قبل الإطلاق»، ومسار مجهول يعرض حالة صادقة.
  - **الموافقات**: الاختيارية (قصص النجاح) قابلة للسحب فعلياً؛ سحب الأساسية يعني إغلاق الحساب، ويُشرح ذلك بدل زر ميت.
- **البدائل المدروسة:** حذف فوري (يخالف فترة التأكيد ويخترع سياسة)؛ اختراع مدة نهائية (قرار بشري ممنوع اختراعه)؛ نصوص قانونية نهائية بلا مراجعة (خطر قانوني).
- **التبعات:** + حقوق مستخدم قابلة للممارسة الآن بصدق. − الحذف غير منفَّذ فعلياً (§8 #29)، والنصوص تحجب الإطلاق (§8 #31).
- **معايير المراجعة:** اعتماد مدة الاحتفاظ، وبناء مهمة المسح في P18، والمراجعة القانونية.
- **المراجع:** `use-account-deletion.ts`, `export-service.ts`, `export-file.ts`, `features/legal/legal-documents.ts`, `locales/*/legal.json`.

## ADR-0022 — عزل واجهات Expo الأصلية في وحدات حدودية
- **التاريخ:** 2026-11-16
- **الحالة:** Accepted
- **السياق:** في P06 فشل افتراضان لواجهات حزم Expo: `expo-image-manipulator` تبيّن أنها تُصدّر `manipulateAsync` لا الواجهة الكائنية، و`expo-file-system` تبيّن أنها تُصدّر الواجهة الصنفية (`File`/`Directory`/`Paths`) والكلاسيكية في `/legacy`. الوكيل لا يملك وصولاً لـ`node_modules` للتحقق، والقاعدة `§1 #6,#14` تمنع التخمين.
- **القرار:**
  - كل استدعاء لحزمة Expo أصلية يُحصر في **وحدة حدودية واحدة** تصدّر واجهة داخلية بسيطة تُستهلك من الـhooks/الشاشات.
  - الوحدات الحالية: `token-vault.ts` (secure-store) · `image-pipeline.ts` (picker + manipulator) · `biometric.ts` (local-authentication) · `export-file.ts` (file-system + sharing).
  - عند اختلاف الواجهة المثبتة، الإصلاح ينحصر في الوحدة + mock اختبارها، ولا ينتشر في الشاشات.
  - **إجراء تحقق مقترح قبل الاعتماد:** `npm ls <pkg>` أو `npx expo install --check`، أو قراءة `.d.ts` المثبتة من قِبَل المالك.
  - mocks الحزم الجديدة تُوضع **محلياً في ملفات الاختبار** إن كان `jest.setup.ts` معدَّلاً خارج الجلسة (تفادي إعادة كتابة ملف غير مرسل).
- **البدائل المدروسة:** استدعاء الحزم مباشرة من الشاشات (ينشر الخطأ)؛ الاعتماد على وثائق من الذاكرة (فشل مرتين)؛ تثبيت إصدارات أقدم لضمان واجهة معروفة (يخالف `expo install --fix` وقاعدة التوافق).
- **التبعات:** + كلفة الإصلاح انحصرَت في ملف + mock في الحادثتين. − طبقة تغليف إضافية صغيرة؛ لا يُلغي الحاجة للتحقق.
- **معايير المراجعة:** توفّر وصول موثوق لملفات الأنواع المثبتة، أو توحيد Expo لواجهاتها.
- **المراجع:** `features/settings/export-file.ts`, `features/profile/image-pipeline.ts`, `features/settings/biometric.ts`, `features/auth/token-vault.ts`, `docs/INTEGRATIONS.md §5`.
